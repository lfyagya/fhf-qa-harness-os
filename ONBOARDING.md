# FHF QA Harness — Workspace Setup

Doc revision: [`docs-2026-09-22`](docs/framework/docs-release.md)

For a QA engineer joining the FHF project. Sets up the automation lanes and the AI harness that
governs them.

**Do not accept a zipped copy of someone else's `FHF` folder.** It carries their database and Okta
credentials, their Cypress Cloud keys, `node_modules`, and 20 git repositories, and it has no way to
receive updates. Everything below is cloned and regenerated instead, which is why it stays current.

These steps are the same on **Linux, macOS, and Windows**. Use whatever shell you already have
(bash, zsh, PowerShell, or cmd). Commands below are `node` and `git` unless a step must set an
environment variable — those three assignment forms are listed together (ADR-0051).

## One command

Same command for a new machine and for an engine update. Run it **from the engine clone**
(`fhf-harness-os` / `fhf-qa-harness-os` — whatever folder you cloned into). It syncs the harness,
then writes `.harness/workspace.local.json` for FHF **and** every testing lane (Cypress e2e,
Cypress smoke, Python backend) from the standard folder names. No form.

```
node scripts/harness/bootstrap.mjs
```

| When | First do this | Then |
|---|---|---|
| **New** | Clone the engine + FHF lanes below | `node scripts/harness/bootstrap.mjs` |
| **Updated** | `git pull` in the engine clone | `node scripts/harness/bootstrap.mjs` |

If sync says files changed since the last sync, stop and ask. Do not use `--force`.

Open Cursor on **`FHF`**, not on a single lane folder. If a lane is still blocked,
`node .harness/setup.mjs` inside that folder infers the same paths (use `--form` only
when your folders are not the standard names).

## Layout

The harness engine sits *beside* the workspace, not inside it. Clone every `treacyandcoventures`
repository into the workspace — automation lanes are writable; product source is read-only.

Home directory below means `%USERPROFILE%` on Windows cmd, `$HOME` / `~` on Linux, macOS, and
PowerShell. Folders can live anywhere; sibling layout is what bootstrap expects.

```
<home>/
├── fhf-harness-os                  the engine — policy, hooks, agents, skills
└── FHF                             the workspace — where you actually work
    ├── .claude                     GENERATED by sync. Never hand-edit.
    ├── .harness                    your local paths + lane marker
    ├── front-end-automation-e2e    front-end-automation @ dev
    ├── front-end-automation-smoke  front-end-automation @ staging
    ├── fhf-backend-automation      @ master
    ├── fhf-dashboards              @ dev, read-only
    ├── fhf-rest-internal           @ dev, read-only
    ├── fhf-rest-service            @ dev, read-only
    ├── fhf-rest-external           @ dev, read-only
    ├── fhf-summer-2016             @ dev, read-only
    ├── fhf_documents               @ master, read-only
    ├── fhf-letters                 @ master, read-only
    ├── fhf-python-utils            @ main, read-only
    ├── fhf-reposession             @ main, read-only
    ├── fhf-serv-agents             @ main, read-only
    ├── fhf-serv-template           @ template, read-only
    ├── fhf-llm-poc                 @ main, read-only
    ├── spark-integrations-tests    @ main, read-only
    └── oracle-instantclient-dependencies  @ master, public, read-only
```

Two things surprise people:

- **The e2e and smoke lanes are the same repository**, cloned twice at different branches. Dev work
  happens on `dev`; production smoke runs from `staging` and is GET-only.
- **Product source lives in the same workspace but is read-only.** Automation never writes to it.
  The GitHub name for repossession is `fhf-reposession` (one "s") — clone that spelling.

## 2. Clone

In a terminal, go to your home directory (or any directory you will keep), then clone. `git` is the
same in every shell.

```
git clone git@github.com:lfyagya/fhf-qa-harness-os.git fhf-harness-os
mkdir FHF
cd FHF
```

On Windows cmd, `mkdir FHF` then `cd FHF` is the same. On PowerShell, `New-Item -ItemType Directory FHF` also works; `mkdir FHF` usually does too.

Lane clones — the folder name is what distinguishes the two frontend lanes, so use exactly these
names:

```
git clone -b dev     git@github.com:treacyandcoventures/front-end-automation.git front-end-automation-e2e
git clone -b staging git@github.com:treacyandcoventures/front-end-automation.git front-end-automation-smoke
git clone -b master  git@github.com:treacyandcoventures/fhf-backend-automation.git fhf-backend-automation
git clone            git@github.com:treacyandcoventures/Test-Case-Automation-Using-Claude-Agents.git
```

## 3. Local paths and harness files

`bootstrap.mjs` already did both: it synced generated harness files and wrote ignored
`.harness/workspace.local.json` files. Do not hand-write that JSON unless your folders
are not named `FHF`, `fhf-backend-automation`, and `Test-Case-Automation-Using-Claude-Agents`.

Confirm from the FHF workspace root:

```
node .harness/verify.mjs change
```

Bootstrap syncs from the engine clone you run it from. **Run it from your own clone, and never
from a stale one:** an out-of-date clone reports current files as hand-edited and offers `--force`,
which would overwrite them with older policy. If it reports files "changed since the last sync",
stop and ask. Do not reach for `--force`.

## 4. Your own credentials

Never copy these from a teammate. Each file has a committed template; fill it with credentials issued
to you.

| Lane | Copy | To | Holds |
|---|---|---|---|
| backend | `tests/example_env` | `tests/.env` | API, Okta, TestRail |
| backend | `config/example_config.ini` | `config/config.ini` | Oracle, S3, email |
| cypress | `.npmrc.example` | `.npmrc` | Cypress Cloud record key |

All targets are gitignored. If `git status` ever shows one, stop and investigate before staging.

`cypress.env.json` is also required and currently has **no committed template** — ask the owner which
keys it needs. (Worth fixing: it should ship a `cypress.env.example.json` like the others.)

## Owner opt-in (gate edits)

A session may change `config/qa-control-plane.json`, `.claude/settings.json`, or `.claude/hooks/`
only when the **agent process** already has `FHF_ALLOW_HARNESS_EDIT=1`. Pasting the name in chat
does not set it. An agent must not set it for itself.

Set it in the terminal, then start Cursor **from that terminal** (or add the variable on the
Cloud Agent environment and start a **new** run):

| Shell | Command |
|---|---|
| POSIX (Linux, macOS, Git Bash) | `export FHF_ALLOW_HARNESS_EDIT=1` |
| PowerShell | `$env:FHF_ALLOW_HARNESS_EDIT = "1"` |
| cmd.exe | `set FHF_ALLOW_HARNESS_EDIT=1` |

Then, from the engine clone:

```
cursor .
```

If the prompt already shows `...\fhf-harness-os>` (or `.../fhf-harness-os`), you are in the engine.
Do **not** `cd /path/to/...` and do **not** run `export` in cmd.exe. That is a POSIX assignment.
In that window:

```
set FHF_ALLOW_HARNESS_EDIT=1
cursor .
```

`'export' is not recognized` means this window is cmd.exe. Use `set`, not `export`.

If `cursor` is not on `PATH`, set the variable, then open this folder in Cursor and start a new
Agent chat. Production-artifact reads use the same three forms with `FHF_ALLOW_PROD_DATA`.

## Staying current

You never need another zip. In the engine clone:

```
git pull
node scripts/harness/bootstrap.mjs
```

Pull the lane repos and the product clones on their own branches as normal. The harness updates
independently of them.

## Known gotchas

**`.npmrc` and the Cypress launch failure.** On Windows the Cypress suite needs `script-shell`
pointing at `Git\bin\bash.exe` — *not* `Git\usr\bin\bash.exe`. The file is gitignored, so a fresh
clone reintroduces the problem, and the symptom is misleading:
`Cannot find module 'C:\cypress\bin\cypress'`. That Bash requirement is Cypress scripts only.

**Backend tooling must be on `PATH`.** Python 3.10 and Oracle Instant Client are picked up by new
terminals only — an already-open terminal keeps the old `PATH`. Activate the venv per session.

**Never `cd` into a repository with no `.harness/workspace.local.json`.** Hooks resolve the working
directory, so a shell parked there goes WORKSPACE BLOCKED and holds a lock. Inspect other checkouts
with `git -C <path>` instead. If it happens, return to the workspace root in the same kind of shell
that took the lock (`cd` / `Set-Location`). A rejected command never runs, so retrying the blocked
`cd` will not clear it.

**`.claude/` is generated.** Edit policy in the engine and re-run sync. Hand-editing it makes the
next sync refuse, and your change is lost the moment someone forces past it.

**`fhf_documents` on Windows.** The Oracle/ORDS tree is still cloned, but a Windows working tree can
fail to check out. If that happens, leave the clone in place and inspect files through Git objects
(`git ls-tree` / `git show`) rather than deleting it.

When setup is done, read [`CLAUDE.md`](CLAUDE.md) for what this repository is and where the
engineering handbook lives.
