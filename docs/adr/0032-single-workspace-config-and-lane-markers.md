# ADR-0032 — Single Workspace Config, Lane Markers Instead of Lane Copies

| Field | Value |
|---|---|
| **Status** | Proposed |
| **Date** | 2026-09-16 |
| **Amends** | ADR-0028 (lane-scoped agent and skill projection) |

## Context

`sync-loader-shims.mjs` writes a full `harness.config.json` into every consumer: the workspace root
and each of the three lanes. The control plane is 2833 lines, so the workspace carries four copies of
it.

On 2026-09-15 three of those four had silently drifted. The root projection matched the engine
exactly; `front-end-automation-e2e`, `front-end-automation-smoke` and `fhf-backend-automation` each
held 31 routes against the engine's 36, and **zero** of their routes carried the `invoke` key that
ADR-0030 had just added. Route-mapped invoke worked at the workspace root and was a silent no-op
inside every lane. Nothing reported this: each copy is valid JSON and self-consistent, and drift is
only visible by diffing against the engine.

It was also actively dangerous. A sync run from a stale engine checkout read those newer files as
hand-edits and offered `--force`, which would have deleted five newly added skills and reverted the
`invoke` work. The projection being duplicated is what made a stale baseline destructive rather than
merely wrong.

The second problem is the assumption underneath lane scoping. ADR-0028 trims each lane's agent and
skill roster to what that lane can act on, which presumes a task belongs to exactly one lane. The
owner's work is end-to-end — frontend and backend in a single task — so a roster trimmed to the e2e
lane withholds the backend agents that task needs. The boundary the projection is organised around
is not a boundary the work respects.

**The mechanism to fix this already exists and is unused.** `harness-config.mjs` resolves the config
from `CANDIDATES`, which are relative to the *hook file's own location* (`HERE`), not the working
directory — so a lane's vendored hooks find that lane's copy and never look further. Meanwhile the
same module already contains two upward walks:

- `markerLane(cwd)` walks up for `.harness/lane.json`, so **lane identity already resolves upward**.
- `hasConsumerProjection(cwd)` walks up for `.claude/harness.config.json` — and throws the result
  away, returning only a boolean to `detectLane()`.

The walk that would find the workspace config from inside a lane is already written. It simply is not
wired into `loadHarnessConfig()`.

## Decision

1. **One authoritative projection, at the workspace root — and nothing in the lanes.**
   `sync-loader-shims.mjs` stops writing `.claude/` into the lanes altogether: not just
   `harness.config.json`, but `agents/`, `rules/`, `skills/`, `hooks/`, `settings.json` and the
   Cursor adapter's `hooks.json`. The workspace root keeps the full set, generated from the engine
   exactly as now. A lane retains only `.harness/` — its lane marker and runtime files.

   The draft of this decision centralised the config and left the rest projected per lane. That was
   half a decision. The duplication it left is what `laneScope` then had to trim, and the trimming is
   what made cross-layer work impossible: the backend repository received 3 of 7 agents and no
   Cypress agent at all, while e2e received 6 of 19 skills and none of the backend generators. The
   question "why does a frontend repo need backend agents?" has one correct answer — it does not, and
   neither does it need a copy of anything else. One set, selected per task.

   Measured after the change: root 7 agents / 18 rules / 19 skills / 41 hooks; every lane zero.

2. **Lanes keep their marker.** Each lane retains `.harness/lane.json` — already generated by
   `laneMarker()` and already read by `markerLane()`. Lane *identity* stays per-lane and is one line;
   lane *policy* moves to the central config, keyed by lane. These are different things, and only
   identity needs to be local.

3. **`loadHarnessConfig()` falls back to an upward search.** `hasConsumerProjection` is generalised
   to return the path it finds rather than a boolean, and that path is appended to `CANDIDATES` after
   the existing `HERE`-relative entries. Ordering is deliberate: an existing local config still wins,
   so the migration is incremental and reversible per lane, and the engine's own
   `config/qa-control-plane.json` keeps resolving as it does now.

4. **Roster trimming is retired; the smoke mutation ban is not.** `laneScope` stops filtering
   `harness.agents` and `harness.skills`, because end-to-end tasks legitimately need both sides.
   Smoke's GET-only restriction is a safety boundary rather than a convenience one and stays enforced,
   selected by lane at runtime through `detectLane()` — which already prefers the marker over any
   path heuristic.

5. **The backend lane is mandatory, not an optional add-on.** `backendRoot` moves from
   `optionalInputs` to `requiredInputs`, and `workspaceContract.lanes.backend` is declared for the
   first time — it did not exist, so `detectLane()` fell through to `"root"` for the backend
   repository and the lane had no operational identity. `syncBackend()` now calls
   `syncRuntimeEvidence()`, which it never did, so the backend repository finally receives
   `.harness/lane.json` alongside the `.claude/` tree it was already getting.

   **A lane is an environment and mutability scope, not a layer.** `e2e` means mutable verification
   against dev; `smoke` means read-only verification against production. Both span frontend *and*
   backend — an end-to-end check of a production dashboard is incomplete if it stops at the UI and
   never reaches the API or Oracle behind it. So `backendRoot` is a required input for **both**
   lanes, not only e2e.

   A first draft of this ADR had smoke keeping `backendRoot` optional, on the grounds that smoke is
   "frontend verification". That reasoning is rejected: it reintroduces the layer-as-lane split that
   this decision exists to remove, and it would leave production smoke blind to the backend half of
   every flow it claims to cover. Smoke's GET-only restriction is unchanged and now reads across both
   layers — read-only against the production frontend *and* the production backend.

   The `backend` entry remains as the **repository's** identity, not a separate scope of work: a
   session opened inside `fhf-backend-automation` still needs a resolvable lane for the hooks to
   load. It keeps `requireBranch: false`, matching e2e, because backend work is task-scoped and a
   ticket branch is its normal state — pinning it to `master` would report every active task as
   not-ready.

6. **Lane variation, if it is ever needed again, goes through the existing overlay.**
   `FHF_HARNESS_OVERLAY` is already validated by `validateOverlay()`, restricted to declared sections,
   and `assertLowerBudget()` permits an overlay only to *narrow* a budget, never widen it. That is the
   sanctioned channel for per-context difference, and unlike a full copy it cannot grant a lane more
   than the central policy allows.

## Consequences

Drift of the kind found on 2026-09-15 becomes structurally impossible: there is one file, so there is
nothing to diverge from. `--force` also stops being destructive in this dimension, because a stale
engine can no longer overwrite three lane copies with an older policy.

A checkout taken *outside* the workspace finds no config on the upward walk. `loadHarnessConfig()`
already throws with a message naming the candidates it tried, and that behavior is kept rather than
softened to a no-op — a harness that silently does nothing is the failure mode ADR-0027 exists to
prevent.

**This cost is real, and larger than first assumed.** The draft of this ADR asserted it was near zero
on the grounds that the projections are local-only and gitignored. Verified 2026-09-16: that is
false. `.claude/harness.config.json` is **tracked in git** in all three lane repositories; only
`.claude/settings.local.json` and `.claude/hooks/.sweep-retries` are ignored. A teammate who clones
`front-end-automation-smoke` on its own gets a working harness today, including the GET-only
production guard, and would get none after this change.

That makes one question decisive, and it is not answerable from the code:

- If every session is opened at the workspace root, decision 1 stands as written.
- If anyone works in a standalone clone of a lane repository — a teammate, a CI job, a second
  machine — then removing the tracked lane config removes their gates, and the smoke lane is the
  worst case because its restriction is the one protecting production.

Until that is settled, the safe subset of this ADR is decisions 2, 3 and 5: wire the upward search,
keep the marker, and keep local configs winning when present. That alone ends the *silent* half of
the problem, because a lane that is missing a key falls back to the workspace copy instead of running
a stale policy. Decision 1 — actually deleting the lane copies — should wait on the standalone-clone
answer.

**Sessions must open at the workspace root.** Config resolves upward; agents, skills, rules and
hooks do not — `hookCommand()` joins `.claude/hooks` off `CLAUDE_PROJECT_DIR`, and Claude Code reads
agents and skills from the project directory, neither of which walks to a parent. So a session
opened inside a lane repository now has no harness at all. That is the accepted cost of a single
set, and it is the one part of this ADR with no fallback.

Two things make it tolerable. The workspace is the unit of work — `ONBOARDING.md` sets teammates up
that way, cloning the lanes inside `FHF`. And the rule that actually protects production is
**path-based**, not lane-based: `isSmokePath()` matches `/smoke/`, so a smoke spec edited from the
workspace root is still guarded, and a session at the root governs every lane file beneath it.

A backend-side gap this exposed and did not close: `tests/smoke/` in `fhf-backend-automation` holds
110 files that run against production, and `validate-backend-automation.mjs` has no mutation check at
all — the GET-only rule was attached to the frontend smoke *repository* rather than to smoke as a
concept. The suite is clean today (verified 2026-09-16: zero mutating calls), so this is a ratchet
waiting to be written, not an active breach.

ADR-0028's projection machinery is not deleted. `laneAllows()` and `harnessConfigTextForLane()`
remain, unused by the default path, so restoring lane scoping is a configuration change rather than a
rewrite if the end-to-end assumption ever stops holding.

What does not change: the engine remains the only authoring surface, `protectedPaths` and the
`FHF_ALLOW_HARNESS_EDIT` opt-in from ADR-0027, the false-green checks, and the agent roster itself.
