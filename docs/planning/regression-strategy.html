1 The Strategy in One Sentence

Run the smallest set of tests that can observe a regression from this change on every PR; build regression coverage sprint by sprint against real business flows; run the full suite before every release. Never let a narrowed run serve as a release verdict.

Regression testing is not "run all tests before a release." It is a continuous practice with three distinct responsibilities: fast PR feedback (did this diff break something?), sprint coverage growth (is this sprint's work automation-covered and regression-protected?), and release confidence (can we state that the product behaves as accepted across every covered workflow?).

Each responsibility has a different answer cadence and a different audience. Collapsing them into a single "run everything" gate is what produces 29-minute PR queues that engineers learn to ignore, or green builds from suites where 13 of 40 specs never started.

What "regression" means precisely

A regression is a behavior that was accepted in a prior run and is now failing. That definition has a structural consequence: you can only claim a regression if the behavior was previously accepted. Today, 0 of 14 E2E workflows satisfy the full acceptance contract (approved intent → verified implementation → automation → exact assertion → execution evidence). That is the honest starting point. This strategy converts that 0 into a growing baseline — one accepted workflow per sprint.

The problem this strategy is solving

The current automation estate has structural volume but cannot yet produce a product-protection claim. Five gaps connect into one root cause:

Root cause: test volume is being mistaken for product confidence. The path forward is not more tests — it is tracing each test to an accepted business risk, and building the cross-lane evidence that makes that trace auditable.

2 Business-Flow Chain Coverage

Module-by-module coverage answers "does this screen work?" Business-flow chain coverage answers "does a loan actually move correctly through its lifecycle?" These are different questions, and only the second one can protect against the class of defects that live at the seams between modules.

The loan lifecycle — our regression spine

Cross-module regression is ordered by the loan's actual movement through the system:

Regression must be planned in this order because downstream modules depend on upstream state. A defect in Titles may surface as a failure in Loss Mitigation; a broken invoice path in Loss Mitigation propagates to Checks. Testing modules in isolation and in alphabetical order misses those seams entirely.

What "full chain" means — UI → API → DB, per business workflow

A full chain is not "the Titles UI test passes." It is a traceable path where the same controlled loan identity moves through every layer:

LayerWhat is verifiedEvidence
UI (Cypress E2E) The correct actor, on the correct screen, performs the business action — and the page reflects the expected state change Cypress Cloud run · screenshot · cy.apiWait() intercept assertion
API (intercepted request) The exact request the UI sent — method, path, payload shape, status code — matches the API contract for this workflow step Network intercept body · configured response-contract validation
DB (Oracle via pytest) The same synthetic loan ID that drove the UI action now has the correct persisted state in the Oracle database — or has explicitly not been written where no write is expected pytest Oracle query · JUnit row · correlated by scenarioId / loan ID

Correlation is the key: the E2E spec and the pytest suite must share the same synthetic loan identity (a controlled ID created in setup, verified in the Oracle assertion, and cleaned up after the run). Without that shared ID, two suites passing in parallel is coincidence — it is not cross-layer evidence.

3 Sprint Regression Framework

Every sprint starts with a scope assessment — not at the end, not at release time. The assessment classifies every ticket and drives two parallel workstreams: covering what needs to be covered this sprint, and growing the permanent regression baseline when sprint work is already handled.

Sprint planning: freeze the regression checklist

At sprint planning, every ticket in scope is classified into one of four buckets. This is a QA scope decision — not a developer decision and not a release-owner decision:

ClassificationMeaningAction
regression_required This ticket changes behavior that needs to be verified before release Map to one or more business regression activities → check automation coverage
not_applicable Infrastructure, refactor, or purely cosmetic — no product behavior change Record reason. No test activity required.
deferred Behavior will be tested — but not in this sprint (dependency, environment) Record reason and target sprint. Do not count as covered.
blocked Cannot be classified — missing spec, missing environment, missing data Record blocker. Escalate. Cannot go to release as blocked.

Once classified, freeze the checklist. If mid-sprint a new task adds a new activity, create a new checklist version — do not modify the frozen one. Comparing a changed checklist to a prior baseline is a meaningless measurement.

The sprint decision tree — what to build vs what to run

↓
Sprint planning complete. All tickets classified.

N
No regression required this sprint → invest QA capacity in full-chain acceptance work (Section 2). Pick the highest-risk unaccepted business flow and build the correlated UI + API + DB scenario.

N

If the sprint has zero coverage gaps: that is a signal to invest in chain-acceptance, not to coast. The regression baseline only grows when QA capacity is deliberately allocated to it when sprint coverage is already handled.

Pre-release regression — what "confident enough to release" means

Release confidence requires all four of the following. Missing any one of them means the release is not confirmed — it is assumed:

#CheckOwnerEvidence
1 All regression_required sprint tickets have a passing run ID QA Frozen checklist entries · run IDs · qa-run-evidence.json
2 Full E2E + backend suite passes in QA environment with the release build SHA QA + CI Trigger 7 full run · release gate passes · build SHA recorded
3 Coverage ratchet passes — no accepted chain removed, no false-green debt added, UI floors not dropped CI gate coverage-ratchet.mjs check exits 0
4 All blocked tickets resolved or explicitly deferred with owner sign-off QA + Release owner Jira status · written deferral decision

4 Tagging and Grouping — Building the Regression Baseline

Tags are how the regression baseline is built incrementally and maintained accurately. A test without a tag is invisible to the regression runner. A test with the wrong tag is noise. The tag system below is designed so the baseline grows sprint by sprint and is always queryable — by lane, by sprint, by workflow, by chain level.

Tag vocabulary — applied at the describe or it level

@regression Test is part of the permanent regression baseline. Applied only once the scenario has a passing run in CI. Never applied to a draft or fallback test.
@chain:partial UI + API intercept is verified but DB state is not yet correlated. Progress marker — not full acceptance.
@chain:full UI → API → DB verified with the same synthetic identity. Counts toward R1 ratchet. Reserved for accepted workflows only.
@sprint-26 Sprint number when this test was added or accepted. Enables "what did this sprint add to the baseline?" reporting. Never changed after the fact.
@wf:funded-to-servicing Business workflow slug. Groups tests that together cover one business flow regardless of which module file they live in.
@p0 Risk priority from the scenario object (priority field). @p0 = financial / compliance / auth. @p1 = operational. @p2 = cosmetic / informational.

How tags drive execution

WhenCypress --grep / pytest markPurpose
PR impact run No tag filter — spec pattern from select-impacted.mjs Fast, change-scoped feedback. Tags irrelevant here.
Sprint regression check @regression @sprint-26 All tests added or accepted this sprint — confirms new coverage works.
Regression baseline run @regression The full accepted baseline — every test that has ever been accepted. This is the pre-release regression set.
Business flow validation @wf:funded-to-servicing Runs every test tagged to a specific business flow — UI + backend in one grouped report.
Release P0 gate @regression @p0 Critical-only fast pass — financial, compliance, and auth. Fails release if any P0 fails.
Full-chain audit @chain:full Shows exactly which workflows have complete UI→API→DB evidence today. This is the R1 ratchet input.

Grouping in Cypress Cloud — the reporting layer

Tags drive execution filtering; Cypress Cloud groups organize the reporting view. Configure one group per meaningful execution scope so results are readable without manual triage:

Group nameContainsReviewed by

sprint-{N}-coverage Tests tagged @sprint-N added this sprint QA at sprint end retrospective
chain-full All @chain:full tests — the accepted workflows QA + release owner — this is the R1 ratchet source
p0-critical All @p0 tests — financial, compliance, auth Release gate — any failure here blocks deploy
wf-{flow-name} Tests tagged @wf:{flow} for a specific business flow Per-flow chain review during sprint

Tag promotion lifecycle — how a test moves from "new" to "baseline"

A test earns the @regression tag through a verified gate — not by being written:

  1. Written: spec exists, scenario object complete, all required fields present. Tagged @sprint-N and @wf:... only.
  2. Passing in CI: the test passes in the target environment (Dev or QA) with a recorded run ID and the deployed application SHA. No fallback markers. No forced retries.
  3. Scenario reviewed: QA confirms the assertion matches the approved intent — not just that it passes.
  4. Tagged @regression: now part of the baseline. R2 ratchet watches it — any regression from this point blocks PR merge.
  5. If UI + API + DB correlated: add @chain:partial → @chain:full when Oracle assertion passes. R1 ratchet floor rises.

A fallback marker disqualifies a test from @regression. A test that logs "Skipping — prerequisite data unavailable" and returns is not a regression test. It is a placeholder. Fix the precondition before promoting the tag.

Impact-based selection — how PR runs stay fast without hiding gaps

select-impacted.mjs maps every changed source path to the specs that can observe a regression in those paths. Deterministic — no LLM, no clock, no network. The escalation rules:

Changed path typeSelection
Module-owned path (e.g. src/modules/titles/)That module's specs only; plus one-hop downstream seams if applicable
Shared component (e.g. src/components/common/Table/)Full run. A shared component has no single owning module.
Auth / session path (e.g. src/services/authAxiosInstance.js)Full run. A broken session invalidates every other result.
Non-source path (docs, README, tooling)Nothing selected.

If a changed module has no automation, the selector emits a coverage gap report rather than silently passing. A module without automation gets "no E2E coverage" in the PR output — not an implied green.

Two blockers to resolve before the strategy is fully live

Blocker 1 — Smoke orchestration: Run 161 left 13 of 40 specs with startedAt: null. Wiring Trigger 8 (post-deploy smoke gate) today produces a false-green deploy verdict from an incomplete run. Gate stays manually disabled until every configured spec starts and any unstarted spec fails the orchestration gate with an explicit reason.

Blocker 2 — Deployed version capture: No run currently records the application SHA it tested. A result without a version cannot be attributed to a specific build. Every trigger must carry the deployed SHA before results feed the release gate or the ratchet.

Eight principles — the decisions that shape every test we write

  1. Risk before volume. Prioritize financial, compliance, authorization, and data-integrity harm. Start from the risk register, not from file counts or story points.
  2. Approved intent first. No approved product contract means no accepted coverage. A passing test against a draft contract is implementation evidence — not product protection.
  3. Cheapest reliable layer. Deterministic logic → unit test. API contract → pytest. Real user journey with state transitions → Cypress E2E. Safe production reads → Smoke. Never use a heavier layer when a lighter one can observe the same failure.
  4. One identity through the chain. The same controlled loan ID must drive the UI action, appear in the intercepted API request, and be found in the Oracle query. Without that, cross-layer evidence is coincidence.
  5. No silent pass. Missing data, disabled suites, fallback markers, stubbed mutations, and missing prerequisite IDs cannot count as coverage. They count as debt.
  6. State ownership is mandatory. Every mutation needs a synthetic identity, a known baseline state, an explicit cleanup, and verification that the cleanup completed. Cleanup failure is a test failure.
  7. Native evidence is authoritative. Cypress Cloud, JUnit, Mochawesome, Allure, TestRail — these are the record. A normalized qa-run-evidence.json joins them; it never replaces them.
  8. Unknown stays unknown. A missing version, environment, result state, or denominator is recorded as UNKNOWN — never converted to zero or assumed to be passing.

Bottom Line

We have solid architecture, real diagnostic signal, and a clear baseline to build from. The gap is not test count — it is the chain from a passing test to a product-protection claim. We close that gap one accepted workflow per sprint: freeze the checklist, cover this sprint's regressions, invest remaining capacity in chain acceptance, and let the ratchet protect what we've built. After four sprints the release gate is evidence-based. After eight it covers every financial and compliance flow in the loan lifecycle.
