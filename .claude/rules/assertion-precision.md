# Assertion Precision — Scope Before You Assert

Any `data-cy`-less assertion (`cy.contains()`, a CSS-class selector, a body-wide exclusion filter like `:not(#some-id)`) is a bet that exactly one matching element exists where you expect it. That bet fails in two directions — both are regressions to catch before merge, not after a Cloud run:

- **False positive**: an unanchored match hits an unintended element (a header, another tab, a nav duplicate) and the assertion passes without checking what you meant. Silent — only surfaces by inspecting the DOM snapshot of a passing run.
- **False negative**: a real, visible element is excluded by an over-broad filter (nav flyouts, hidden duplicates, portal-rendered content) and the assertion times out even though the page is correct. Looks like a regression; wastes an investigation confirming it isn't.

## Rule

Before shipping any text/class-based assertion:

1. **Grep the app source** (`fhf-dashboards`) for every place that string/class could render on the same page — headers, other tabs, nav links, breadcrumbs. See [[source-map]].
2. **Scope to the narrowest known-stable container**, not a body-wide exclusion filter. Prefer a component root class or `data-cy` hook over `:not(#flyout-menu)`-style negation — negation-based scoping breaks silently the moment the excluded element's structure changes upstream, and it can't tell you *why* it failed.
3. **Check for portals before assuming a wrapper scope works.** Dropdowns/menus/modals built on `menuPortalTarget`, `ReactDOM.createPortal`, or similar render outside their logical component's DOM subtree — scoping to that subtree will exclude real, correctly-rendered content. Grep the component for `Portal` before scoping its content to a parent container.
4. If source confirms the string renders exactly once on the page and isn't a substring of anything else, an unscoped `cy.contains()` is fine — don't add defensive scoping with no real collision risk (YAGNI).
5. **Before picking a root-container class, grep how many components share it** ([[ui-config-hierarchy]]). If 2+ modules render the same wrapper class, the scope constant belongs in `common.ui.js` (e.g. `COMMON_UI.DASHBOARD_ROOT`), imported by each module config — not redeclared per module with a different value that happens to work. Two different selectors doing the same job in two files is itself a defect, even if both pass.
6. **Never disambiguate between multiple matched elements by DOM position (`.first()`/`.last()`/`.eq(n)`) when the elements differ in *kind*, not just position.** Position is not identity — a list can reorder, grow, or shrink for reasons unrelated to your test. Find a structural discriminator instead: a class, attribute, or ancestor that's actually true of "the kind of element you mean" and false of the others (e.g. a class only ever applied to the row type you want). If you must fall back to position because no discriminator exists, say so in a comment and name the ordering assumption explicitly (e.g. "parent renders immediately before its own children").
7. **The test name is a claim — check the assertions actually make it, and check the claim is true before encoding it.** "Visible and enabled" in a title with only a `.should('be.visible')` in the body is silently under-testing. But don't reflexively bolt on the missing half either: trace the control's real default state in source first (e.g. `disabled={someCondition}` gating logic) — if the claimed state is only true after an interaction (a row selected, a toggle flipped), either drive that interaction first or correct the claim to match the actual default. Also check *how* "enabled" is implemented before asserting it: `.should('be.enabled')` only means something for native form controls (`button`/`input`/`select`/`textarea` with a real `disabled` attribute) — a `<div>`/`<span>`-based custom control that fakes disabled via CSS classes (`cursor-not-allowed`, `opacity-50`) will pass a native `:enabled` check trivially, checking nothing.

8. **A class/data-cy value matching where you expect it is not proof it's unique — grep every producer before trusting it.** Finding the selector rendered by the component you *think* owns it is not the same as confirming no *other* component in the app emits the identical value. Two failure directions, both real incidents (see below): (a) the selector is too broad — it also matches an unrelated, ungated element, so a `.should('not.exist')` boundary check can never pass regardless of the real access state, and a passing-looking failure gets misread as a production finding; (b) the selector is non-unique across siblings of the same kind (one instance per column, per row, per tab) — an unscoped `cy.get()` silently asserts against the *first* match, which may not be the one you interacted with. Before trusting a class or `data-cy` value: grep the **whole** app source for every place that exact string is emitted (not just the component whose name matches your mental model), and if it renders more than once per page, scope with `.within()`/`.filter()` to the specific instance you drove, not just the first.

9. **Interaction mechanics are a source fact, not a plausible guess — confirm the real trigger, submit condition, and input constraints before writing the step.** "Click the element that looks like the control" and "type a value and expect it to take effect" are both assumptions until verified against the component's actual event handlers: the true click target may be a nested icon inside the element you clicked, not the element itself; typing may require an explicit submit (Enter, blur, a separate button) rather than firing on every keystroke; an input may silently truncate at a `maxLength` shorter than the string you chose. Grep the component for its `onClick`/`onChange`/`onKeyDown` handlers and any length constraint *before* picking the interaction, not after the first failure explains it back to you.

## Evidence this rule exists

`ancillaryGeneralDashboard.cy.js` (Cloud run 88): 5 tests failed via `containsVisible()`'s body-wide `:not(#flyout-menu)` filter, timing out on text (`'Ancillary'`, tab labels, dropdown trigger) that was actually rendering correctly — confirmed by sibling assertions in the same render tree (table, buttons, badges) passing in the same run. Fixed by scoping to the dashboard's root wrapper instead of excluding the flyout. One of the five (`assertAncillaryGeneralDashboardSelector`) needed the opposite adjustment too: its dropdown *options* render via `menuPortalTarget={document.body}`, so only the inline trigger got scoped — the portal-rendered option checks stay unscoped on purpose.

Same bug recurred in `ancillaryFollowupDashboard.cy.js` (identical `containsVisible()` timeout, different spec). First-pass fix scoped it to `.dashboard-container` while the General Dashboard fix used `.ancillary-dashboard-wrapper` — two different selector values for the same job, in two different files. Both dashboards' root `<div>` actually carry `.dashboard-container` (General: `"ancillary-dashboard-wrapper dashboard-container dashboard-v2-design pl-[51px]"`, Followup: `"dashboard-container dashboard-v2-design pl-[51px]"` — the same class, shared by 18+ dashboard modules). Consolidated to `COMMON_UI.DASHBOARD_ROOT = '.dashboard-container'` in `common.ui.js`, imported by both module configs as `PAGE.ROOT` — rule 5 above exists because of this.

`assertAncillaryFollowupNotesIconHidden` (rule 6): a Notes column cell is empty only when write access is denied *and* the row is a genuine loan-level sub-row — the parent admin/dealer group row always shows `"–"` regardless of access (`parentHidden: true`, unrelated business rule). First fix guessed `.first()` (assumed sub-rows always render after being revealed); still failed. Second guess was `.last()` (assumed the last matched cell must be a sub-row); also failed — verified via the failing `<td>`'s own class list (`border-b border-b-blue-grey-700`, which per source is *exclusively* the group-row modifier, never the sub-row one). Both guesses failed because sub_rows didn't even exist in the DOM yet (TanStack's expand state defaults to collapsed) — no position in that list was ever a sub-row. Fixed by expanding a row first, then filtering by `bg-white`/`bg-blue-grey-900` — a class TanStack only ever applies to sub-row cells, never group rows. That structural filter is what rule 6 exists to push you toward before reaching for `.first()`/`.last()`.

`assertAncillaryFollowupHeaderButtons` (rule 7): test title claimed "Export CSV and Bulk Action buttons are visible **and enabled**," but the command only ever asserted `.should('be.visible')` on both. Export CSV is a real `<button disabled={isExportingCSV}>` (`Button.tsx:94-96`) — enabled by default, safe to add `.should('be.enabled')` directly. Bulk Action is a `<div>`-based `MenuDropdown` trigger with no native `disabled` attribute at all (`MenuDropdown.tsx:39` just omits the click handler; disabled state is CSS-only, `cursor-not-allowed opacity-50`) — and `bulkMenuDisabled = allSelectedRows.length === 0` (`AncillaryFollowup.tsx:636`) means it's **disabled by design** with zero rows selected, i.e. on every fresh page load. Bolting on `.should('be.enabled')` here would have asserted the opposite of real default behavior. Fixed by asserting the actual default (visible + disabled, checked via the CSS class) and correcting the test title to match, rather than forcing the assertion to fit a title that was wrong.

**Custodian tracker dashboards smoke suite (2026-07-10), three separate incidents from source-grep-only exploration with no live verification** — rules 8/9 exist because of these:

- Rule 8(a): a write-boundary check (`.cell-meat-ball-wrapper` `not.exist`) failed on live prod for the read-only account and was first read as "the smoke account holds `CUSTODIAN_WRITE`" — a false production-access finding. Re-investigation found the class is emitted by **two unrelated components**: the write-gated row-action menu (genuinely gated) and an always-rendered, ungated per-field sort dropdown that the filter panel renders once per sortable column — 8-10 of the latter render on every page load regardless of access, which is what the selector actually matched. Fixed by re-scoping to a class emitted by exactly one component. The user caught this by pushing back on the conclusion rather than accepting it — the agent should have re-verified selector uniqueness before reporting a production finding.
- Rule 8(b): a sort-dropdown check (`cy.get(SORT_ASC).should('be.visible')`) failed because `SORT_ASC`'s `data-cy` value is **not unique** — the shared header component renders one asc/desc pair per column, each inside that column's own closed dropdown. The unscoped `cy.get()` asserted on column 0's (closed) pair regardless of which column was actually clicked. Fixed with `.filter()` to real data-column headers, then `.within()` to scope the check to the specific header opened.
- Rule 9: an empty-state search test typed a no-match term but the check failed twice, from two different unverified assumptions in the same interaction — first, typing alone never applied the filter (the component only calls its search-apply function on the Enter keydown, not on every keystroke); second, after fixing that, the typed string was silently truncated by the input's `maxLength`, which only surfaced once a `have.value` assertion was added to check the type actually landed.

Not hook-enforced — `cypress-gate` must flag any new `cy.contains()`/class selector that lacks either (a) a narrow container scope or (b) a one-line justification for why it's safely unscoped. Rule 8's cross-file duplicate-`data-cy`-value case is now partially hook-enforced — see `validate-cypress-rules.mjs`'s ui-config duplicate-selector check, added the same day.
